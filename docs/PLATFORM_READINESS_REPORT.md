### 2026-08-25 (sixth pass) — mutation-level RBAC test completed: mixed, real result

The prior pass identified two genuine write forms (`/feedback`, `/identity-verification`) rendered identically to admin and auditor, but deliberately did not submit either because the console's data-persistence location was unknown. **Root-caused this pass:** the console writes into the *same* Moodle MySQL instance, under `kost_console_*`-prefixed tables (`kost_console_feedback`, `kost_console_identity_verifications`, `kost_console_incidents`, `kost_console_incident_events`) via a separate read-write credential set (`MYSQL_RW_*` env vars on the console container) — found by listing tables matching `%kost%` rather than only `%external%`. This unblocks direct verification and safe cleanup.

**`/identity-verification` — correctly, server-side restricted.** Loading the page as `console_auditor` renders no form at all; instead the server renders "Your role (auditor) is not authorized to record identity verifications." directly (confirmed via `curl`-equivalent DOM inspection: `input[name="candidateUsername"]` has zero matches for auditor, one match for admin). This is an SSR-level gate, not a client-side hide — a genuine pass. The page's own copy explicitly names the intended roles ("Only visible to Administrator / Exam Manager / Instructor roles"), independently corroborating the product's own documented intent that those three roles should exist (see the RBAC gap finding above) — this is now evidence *from the console's own UI text*, not just the login page's claim.

### 2026-08-25 (sixth pass) — every non-a11y cross-browser failure root-caused and fixed; Gate H now CLEAN

3. **WebKit-family genuine latency, not malfunction** — `webkit-desktop`/`tablet-safari` were consistently 10-20x slower than Chromium/Firefox for identical operations (20-40s vs 1-3s) while still eventually succeeding. Gave those two projects a longer per-assertion timeout (25s) so the existing retry has real headroom.
4. **Moodle login-token race** — submitting the candidate login form immediately after page load occasionally bounced back to `/login?loginredirect=1` on WebKit-family engines (reproducible 2/2 on `tablet-safari`) and once on Firefox — consistent with the CSRF `logintoken` being tied to a session cookie that hasn't fully round-tripped yet in some engines.
