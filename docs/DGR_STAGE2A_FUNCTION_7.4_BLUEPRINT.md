entrepôt, de charger et décharger des unités de chargement (UC), et de
charger et décharger des compartiments de fret des aéronefs.*

**Status: PROVISIONAL — SUBJECT TO SOURCE-ITEM DRAFTING, TIER A REGULATORY
GATING, QUALIFIED-INSTRUCTOR VALIDATION, AND ANAC ACCEPTANCE.** Every count
below is a **source-yield ceiling**, not a target to pad toward — per the

**Do not assume Function 7.1's, 7.2's, or 7.3's counts, block structure, or

## Method

For each of the 37 leaf sub-tasks, the count is derived from the "Coverage
assessment" / "KOST course trace" / "Exam/practice trace" columns already
recorded in `docs/DGR_STAGE1_FUNCTION_7.4_DRAFT.md`'s sub-task enumeration
tables (independently re-verified in the cross-validation pass), converted to
a provisional ceiling using this banding — anchored to *this function's own*
slide-span and exam/practice cross-reference counts, not copied from any
other function's numbers:

| Stage 1 coverage assessment | Typical evidence pattern in this course | Ceiling band |
|---|---|---|
| Very strong | Multi-slide (6+ slides) span, worked examples, 3+ exam/practice cross-refs | 6–8 |
| Strong | Dedicated slide(s), clear exam/practice trace or named worked example | 3–4 |
| Strong, shared evidence base (lifecycle-stage reuse) | Dedicated slide(s), but content pool shared across 2–3 nominally distinct official sub-tasks | 2–3, with a binding distinct-framing restriction |
| Adequate / adequate-but-shallow | Pointer-level or single-fact coverage | 2 |
| Adequate, shared evidence base only | Same content pool as another sub-task, no independent reinforcement | 2, with a binding distinct-framing restriction |
| Generic-awareness-only (0.6.2) | States an obligation exists, no procedural detail | 1, sample 0–1 |
| Thin/adjacent, not a clean match (0.4.3) | Passing mentions only, wrong pedagogical stage | 1, sample 0–1, restricted framing |
| Partial coverage (6.1.6) | One half of a two-part official sub-task strongly evidenced, the other half absent | 1, sample 0–1, restricted to the evidenced half only |
| SOURCE GAP | No slide, exam, or practice-book content found anywhere | 0 |

**Sample** = the recommended maximum number of items drawn from that
sub-task's pool for a single exam sitting, the same convention used in
`docs/DGR_STAGE2A_FUNCTION_7.2_BLUEPRINT.md` and
`docs/DGR_STAGE2A_FUNCTION_7.3_BLUEPRINT.md`. It is a per-sub-task draw
ceiling, not a claim every sub-task must appear every sitting.

## Binding caveats carried into this blueprint

1. **4.2.5 / 6.1.1 / 6.3.4 — "transporter le fret [...] jusqu'à/à
   l'aéronef/l'entrepôt/l'aérogare" — confirmed SOURCE GAP, all three. Count
   = 0 for all three, no exception.** Independently reconfirmed in the
   cross-validation pass by an exhaustive keyword search (`achemin*`,
   `convoy*`, `camion`, `tracteur`, `véhicule`, `chariot`, `tarmac`, `aire de
   trafic`, `piste`, `remorque`, `dolly`, `tractage`, `navette`) across the
   full 155-slide course, the 20-question exam, and the 20-question practice
   book — zero matches in all three documents. No course material anywhere
   addresses the physical movement of cargo between warehouse and aircraft as
   a distinct taught step. **Do not draft any item against these three
   sub-tasks without new KOST material or direct Tier A DGR text.**
2. **6.1.6 "Informer le commandant de bord et l'agent des opérations
   aériennes ou le régulateur de vols" — partial-gap decision: count = 1,
   sample 0–1, restricted to the well-evidenced half only.** The captain
   ("commandant de bord") notification half is strongly evidenced (NOTOC
   slides p.135–141, explicit "correspondance exacte" wording, practice book
   capstone Q20). The flight-ops/dispatch half ("agent des opérations
   aériennes" / "régulateur de vols") has zero evidence anywhere in the
   course, exam, or practice book — independently reconfirmed by keyword
   search in the cross-validation pass. **Decision and justification:** this
   sub-task keeps a minimal, non-zero ceiling because the captain-notification
   obligation is a real, distinctly testable fact in its own right (a
   role/responsibility question — *who* must be informed before departure —
   not a NOTOC-content-accuracy question). It is not raised to a larger count
   because (a) only half the official sub-task is evidenced, and (b) its
   evidence base already substantially overlaps with 6.1.5's own pool (both
   draw on the same p.135–141 NOTOC slides), so a larger 6.1.6 count would
   risk duplicating 6.1.5's items rather than adding independent value. **Any
   item drafted from this pool must be framed as a notification-obligation
   question (who must be informed) and must never test informing "l'agent des
   opérations aériennes" or "le régulateur de vols" — that half remains an
   open SOURCE GAP.**
3. **0.4.3 "Envisager de multiples dangers" — thin/adjacent evidence
   decision: count = 1, sample 0–1, restricted framing.** Unlike Function
   7.3 (three dedicated classification-stage slides with a named table and
   exceptions list for this identical sub-task) or Function 7.2 (a confirmed
   total SOURCE GAP), Function 7.4's course only mentions "risques primaires
   ou subsidiaires" twice, both in an operational context (loading-separation
   p.106, NOTOC content-field list p.137) — independently re-located at
   exactly those page numbers in the cross-validation pass. Neither mention
   teaches how to *determine* a primary vs. subsidiary hazard (this
   sub-task's own subject matter, DGR 3.10-equivalent); both simply
   acknowledge a package may already carry more than one hazard label by the
   time it reaches the warehouse/loading stage. **Decision:** a minimal,
   non-zero ceiling is kept because the operational-context fact itself is
   real, distinctly stated evidence (not inference) — but any item drawn from
   this pool must test only that operational-stage awareness fact (stowage/
   separation rules under DGR 9.3.2.1 apply to every hazard label on a
   package, primary or subsidiary), grounded in the p.106/p.137 evidence.
   **No item may test a classification-stage "determine which hazard is
   primary" procedure — that determination method is not taught anywhere in
   this course.**
4. **Six sub-tasks share evidence pools across lifecycle stages — kept as
   separate small pools with a binding distinct-framing restriction, not
   merged and not independently re-inflated.** The Stage 1 draft's SOURCE GAP
   note 4 records that the course does not cleanly separate pre-loading
   warehouse inspection from in-aircraft-loading inspection from post-flight
   unloading inspection, unlike IATA's table's three-stage structure:
   - **Hidden-DG package verification** is shared across **four** official
     sub-tasks, not three: the Block 0 general-awareness leaf **0.2.1**
     (already counted above at its own ★-level band) plus the three ★★★
     operational-stage leaves **4.2.1** (pre-load), **6.1.2** (at loading),
     **6.3.2** (at unloading) — all four draw on the same p.48–52 slide
     range.
   - **Damage/leak verification** is shared across three ★★★ operational-
     stage leaves: **4.2.2** (pre-load), **6.1.3** (at loading), **6.3.3**
     (at unloading) — all three draw on the same p.101–103 slide range.
   - **Decision:** each of the six operational-stage leaves (4.2.1, 6.1.2,
     6.3.2, 4.2.2, 6.1.3, 6.3.3) keeps its own separate, modest pool (2–3
     each, see per-item tables below) rather than being merged into one pool
     or zeroed out — IATA's own table treats them as genuinely distinct
     procedural checkpoints (pre-load / loading / unloading), the same
     reasoning `docs/DGR_STAGE2A_FUNCTION_7.3_BLUEPRINT.md`'s caveat 4 used
     for its own analogous shared-evidence case (3.1.4/3.2.5). **Binding
     drafting instruction: every item drawn from these six pools must test
     the distinct lifecycle-stage procedural context it officially sits at
     (warehouse pre-load / aircraft loading / aircraft unloading), not
     restate the same underlying fact three or four times with only the
     stage name changed.**
5. **7.1 + 7.2 (accident vs. incident reporting) — treated as ONE combined,
   dual-tagged pool, following `docs/DGR_STAGE2A_FUNCTION_7.2_BLUEPRINT.md`'s
   precedent for the identical evidence pattern.** The Stage 1 draft confirms
   "accidents" and "incidents" share one slide (DGR 9.6.1, p.150) with no
   independently-worded treatment of either term — the same pattern already
   confirmed for Functions 7.1, 7.2, and 7.3's own material (now a
   four-times-confirmed cross-function pattern). Drafting two artificially
   "different" pools from one undifferentiated slide would require inventing
   a distinction the source does not make. **A produced item counts toward
   satisfying both 7.1 and 7.2's coverage simultaneously, not as two separate
   items.** If future source material draws a genuine accident/incident
   distinction, this decision should be revisited.
6. **0.2.2 carries an interpretive-mapping uncertainty, explicitly flagged,
   not silently resolved.** Because 7.4's own 0.2.1/0.2.2 wording split moved
   the "hidden goods" concept into 0.2.1 (see cross-validation finding (b)),
   the Stage 1 draft made a judgment call mapping 0.2.2's broader
   "potentially dangerous merchandise" wording to the
   prohibition/approval/derogation/exception/exemption slide material
   (p.35–44) rather than re-citing the hidden-DG slides a second time. This
   blueprint's count for 0.2.2 (3) is built on that mapping. **A future
   qualified-instructor pass should re-examine whether this mapping is the
   correct interpretation of 0.2.2's official scope for this function before
   items are finalized.**
7. **0.6.2 (employer emergency-response requirements) is generic-awareness
   only.** Independently confirmed: the course states an employer procedure/
   information must exist and be available to the commandant de bord,
   without describing any specific employer's actual procedure. The bank may
   test that personnel must know/follow the employer's procedure; it must
   never invent employer-specific procedure content — the same constraint
   already applied to this identical leaf in every prior function's
   blueprint.
8. **The "Cadre CBTA" matrix for Function 7.4 is confirmed useless and
   contributes zero evidence to any count below.** Independently reconfirmed
   in the cross-validation pass: it describes cabin-crew (PNC) in-flight
   duties and cites IATA Tableau 1.5.A, not this function's own TABLEAU
   7.4.A. No count in this blueprint relies on it.
9. **Course baseline is the DGR 66th Edition, not the current 67th
   Edition/Addendum 1.** Every regulatory paragraph, table, and figure number
   cited as evidence below (e.g. DGR 9.3.2.1, Table 9.3.A, Table 10.5.C,
   Table 10.9.3.7, 148×210 mm ULD label dimension) is Tier B (as displayed by
   the KOST slides), not yet Tier A–verified against the current 67th
   Edition/Addendum 1 text. This blueprint fixes *how many questions per
   sub-task the source can support* and *why*, not final question wording or
   regulatory correctness — a separate, later Tier A gate.
